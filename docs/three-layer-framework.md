# 三层框架：事实层 / 表面层 / 手感层

小说写作没有编译器。代码 Agent 显得自然，不是因为约束少，而是因为它的约束在**环境里**——编译器、类型检查、测试是廉价、可反复调用的外部真值源。写作把验证器塞进了提示词，于是既不可靠（模型可以忽略），又昂贵（和写作本身抢注意力），还倾向于把创作压向均值。

本框架的立场是：**不要给创作加更多规则，而是把可验证的部分做成真的验证器，把不可验证的部分从规则里拿出去。**

判断一条约束归哪一层，只问两个问题：

1. 它有客观真值吗？
2. 它的违反能被逐字引用吗？

两个都是 → 表面层（确定性门禁）。第一个是、第二个部分是 → 事实层（契约 + 语义终审）。第一个否 → 手感层（不做门禁）。

---

## 一、事实层：契约 + 终审

**真值源**：`WritePack`（写前编译出的事实包）+ `NarrativeEvidencePacket`（角色卡、写作记忆、已读原文）。

### 契约（`src/fact_contract.ts`）

写前编译层交给 Writer 的是一份**承诺**：这些事实成立、这条信息必须落地、这个空白不得补写、叙述不得越过这个视角和认知边界。此前没有任何环节检查成稿是否兑现了承诺——`coverageGaps` 只衡量「写前读够了没有」，终审根本看不到写作包。**没人验证的承诺是提示词，不是约束。**

`buildFactContract(path, pack)` 把写作包归一成可寻址的承诺条目：

| kind | 来源 | 违反时判定为 |
| --- | --- | --- |
| `must_land` | `mustLand` | `commitment_unmet` |
| `known_fact` | `knownFacts` | `fact_conflict` |
| `do_not_invent` | `doNotInvent` | `unsupported_fact` |
| `viewpoint` | `viewpoint` | `knowledge_leak` |
| `knowledge_gate` | `knowledgeGates`（只取「不知道 / 在隐瞒」） | `knowledge_leak` |

`knows` 不进契约：它授权正文，而不约束正文，没提到不构成违约。

契约在证据型 Writer 生成正文时写入 `ToolExecutionContext.factContracts`，与正文同源、同一轮有效。

### 验证

验证交给终审模型，**不做正则**。「这条信息有没有自然落地」是语义判断，用模式匹配既会漏报也会误伤合法正文——这也是 `agents.md` 禁止用正则匹配语义的原因。

确定性的部分只有契约本身：稳定 id、稳定 hash、以及「终审判的就是 Writer 被交付的那份承诺」这一保证。

`buildFactualChapterReviewContext` 把 `factContract` 注入终审上下文，并明确：契约不是文风要求，正文不必逐条复述；每条违约必须能引用正文原文，引不出就不要报。

### 闭环

契约违约不需要专门通道：它以普通终审 blocker（带逐字证据）返回 → `directReviewRepairPacket` → S1 的定向修订路径 → `write_file(path)` 省略 content → 持有同一事实包的 Writer 做有界修订。

```
写作包 → 契约 ─────────────┐
   ↓                      ↓
证据型 Writer → 正文 → 终审（对契约判定）→ blocker+证据 → 修订包 → 定向修订 → 正文
                                                                       ↑____________|
```

## 二、表面层：确定性门禁登记表

**判据**：确定 + 可逐字引用。允许阻断。

`src/surface_gates.ts` 把门禁做成登记表而不是控制流分支。每条声明：

- `id`
- `scope`：`any` | `narrative`（仅章节/番外正文）
- `severity`：`block`（驳回）| `note`（只报告，不往返）
- `describe`：一行说明，供规则盘点
- `run(input)`：纯函数，返回 finding 或 undefined

当前登记：

| id | scope | severity | 说明 |
| --- | --- | --- | --- |
| `dialogue_format` | narrative | block | 对白引号、说话人标注与段落归属 |
| `card_register` | narrative | block | 角色卡措辞被直接搬进对白或贴身叙述 |

元信息泄漏（`gateProseMetaLeaks`）和文风门禁（`gateProseStyleWithSparseAutoRepair`）不在登记表内：它们会**改写正文**，与纯检查结构不同，因此在登记表之前单独运行。

两条纪律：

- 需要判断「写得好不好」的规则不属于这里，属于终审。
- `note` 是真选项。值得提示但不值得一次往返的规则应当**降级**，而不是删掉或继续阻断。

所有阻断项一次性合并成单个修订包上报（`mergedSurfaceGateError`）：一次提交换一轮修订，而不是一道门禁换一轮。

### 规则盘点

登记表的目的就是让盘点成为可能。一条从未真正拦下过东西的规则、或经常被判定为误报而放行的规则，是**负价值**——它只稀释注意力。盘点时对每条问一句：它是在告诉 Agent「你这里错了」，还是在告诉它「你现在该做第几步」？后者应改写成前者，或删掉。

## 四、不变量 vs 固定工作流

`agents.md` 要求尽量不用固定工作流。判据不在约束多少，而在**谁决定下一步**：

- **不变量**：随时可查、失败可定位、不规定顺序 → 与 agentic 兼容。编译器不会让写代码变成固定工作流。
- **阶段图**：规定顺序、规定何时做什么 → 就是固定工作流。

本框架三层全部是不变量。Agent 何时读、何时写、何时提交仍由它按工具结果自主决定；框架只保证「提交时会被什么检查、失败会拿到什么」。
